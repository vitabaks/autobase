# Autobase Console

Autobase Console Community Edition (CE) provides a simple web interface for lightweight deployment of PostgreSQL clusters. It is designed for initial cluster deployment and does not include ongoing cluster management. Full lifecycle management and other advanced capabilities are available in [Autobase Enterprise Edition](https://autobase.tech/docs#getting-started).

Autobase Console CE consists of two main components:

- **Console** — an application stack comprising a UI, API, and database for configuring and launching cluster deployments.
- **Automation** — an Ansible-based layer of playbooks and roles that provisions PostgreSQL clusters.

Console and Automation are tightly integrated: users configure a cluster in the UI, which sends the deployment request to the API. The API then invokes the required [Ansible playbooks](../automation/playbooks/).

## Console Stack

The Console stack includes the following core components:

- **Console UI**: A web interface for configuring cluster deployments and viewing their status.
- **Console API**: A REST API that receives deployment requests from the UI, reads from and writes to the database, and starts the Automation container.
- **Console DB**: A PostgreSQL database that stores cluster configurations, server details, settings, and deployment results.

### Architecture

```
             +-------------------------- Autobase ---------------------------+
+------+     | +------------+    +-------------+    +----------------------+ |     +---------------------+
| User | --> | | Console UI | -> | Console API | -> | Automation (Ansible) | | --> | PostgreSQL Clusters |
+------+     | +------------+    +-------------+    +----------------------+ |     |        1..N         |
             |                           v                                   |     +---------------------+
             |                    +------------+                             |
             |                    | Console DB |                             |
             |                    +------------+                             |
             +---------------------------------------------------------------+
```

- The user defines the cluster configuration in the UI, which sends a deployment request to the API.
- The API stores configuration and deployment data in the database and launches the Automation container.
- Automation uses the inventory and variables generated by Console to provision PostgreSQL clusters on the target servers.
- Deployment progress, results, and cluster status are displayed in the UI.

## Quick Start

> [!NOTE]
> Run Autobase Console in the same network as the target database servers so that it can deploy clusters and collect status information.

### Single Container

Run Autobase Console as a single container:

```sh
docker run -d --name autobase-console \
  --publish 80:80 \
  --env PG_CONSOLE_AUTHORIZATION_TOKEN=secret_token \
  --env PG_CONSOLE_DOCKER_IMAGE=autobase/automation:latest \
  --volume console_postgres:/var/lib/postgresql \
  --volume /var/run/docker.sock:/var/run/docker.sock \
  --volume /tmp/ansible:/tmp/ansible \
  --restart=unless-stopped \
  autobase/console:latest
```

For other deployment options, see the [Deployment](https://autobase.tech/docs/category/deployment) documentation.

### Docker Compose

1. Clone the repository:

   ```sh
   git clone https://github.com/autobase-tech/autobase.git
   ```

2. Navigate to the `console` directory:

   ```sh
   cd autobase/console
   ```

3. Create a local environment file:

   ```sh
   cp .env.example .env
   ```

4. Set the authorization token in `.env`:

   ```sh
   AUTH_TOKEN=your-secret-token
   ```

#### Basic Setup

Use this setup to run Autobase Console without automatic SSL certificate management.

```sh
docker compose up -d
```

Open `http://autobase-server-ip` and enter the value of `AUTH_TOKEN` to sign in.

#### Setup with SSL

Use this setup if you have a domain name and want Caddy to obtain and renew SSL certificates automatically.

1. Create a DNS A record that points your domain to the IP address of the server running Autobase Console.

2. Add the domain, email address, and authorization token to `.env`:

   ```sh
   DOMAIN=autobase.your-domain.com
   EMAIL=admin@your-domain.com
   AUTH_TOKEN=your-secret-token
   ```

3. Run Docker Compose with Caddy:

   ```sh
   docker compose -f docker-compose.caddy.yml up -d
   ```

Open `https://autobase.your-domain.com` and enter the value of `AUTH_TOKEN` to sign in.

## Notes

- The basic setup exposes the Console UI on port 80 without SSL.
- In the SSL setup, Caddy obtains and renews certificates for your domain automatically.
- Data is persisted in the `console_postgres` and `dbdesk_studio_data` Docker volumes, as well as `caddy_data` when using Caddy.
- Docker Compose creates the required networks automatically.
- All services are configured to restart automatically unless stopped manually.
- For additional environment variables, see the [Console API configuration](./service#configuration).

## Using Docker Secrets

Sensitive values, such as the authorization token and database password, can be supplied through files mounted under `/run/secrets` instead of being stored as plain text in `.env`. The Autobase Console images support the `_FILE` convention used by the official `postgres` image: if `FOO_FILE` is set, the contents of that file are used as the value of `FOO`. Setting both `FOO` and `FOO_FILE` to non-empty values is an error.

Use the provided `docker-compose.secrets.yml` override:

```sh
mkdir -p ./secrets && chmod 700 ./secrets
printf '%s' 'your-secret-token' > ./secrets/auth_token
printf '%s' 'your-db-password'  > ./secrets/db_password
chmod 600 ./secrets/*

docker compose -f docker-compose.yml -f docker-compose.secrets.yml up -d
# or, with Caddy:
docker compose -f docker-compose.caddy.yml -f docker-compose.secrets.yml up -d
```

For a Docker Swarm deployment, replace the `file:` sources in the override with `external: true` and create the secrets with `docker secret create`.
